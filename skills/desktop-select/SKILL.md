# Desktop Select

**녹화창을 열어 달라는 요청**에는 `scripts/desktop_select.py recorder --request <로컬 JSON 파일>`을 사용한다. 호스트가 `{"command":"record","task":"작업 이름","exe":"Example.exe","window":"정확한 업무 창 제목"}`을 UTF-8로 쓴다. `window`는 사용자가 지목한 창의 제목 전체를 보존한다. 제목이 같은 창을 구별할 때는 확인된 `hwnd` 숫자도 넣는다. 검토는 `command=review`와 `task`, 보완 녹화는 `command=continue-recording`과 `task`에 필요한 `from_step`, `save_as`, `supplement`만 넣는다.

Python을 직접 호출하고 대화로 돌아와야 하면 호스트의 백그라운드 실행 기능으로 같은 호출의 출력을 이어 읽는다. PowerShell의 `Start-Process -ArgumentList`는 배열을 문자열로 합치므로 사용하지 않는다. JSON 한 줄에서 `status=recorder_ready`를 받으면 “녹화창이 열렸습니다”라고 안내한다. 실제 녹화는 사용자가 **시작**을 누르면 진행된다. 같은 호출의 최종 응답으로 저장, 취소, 오류를 구분한다. 준비 신호 없이 먼저 종료되면 그 응답의 진단을 확인하고, JSON이 없으면 표준 오류와 종료 코드를 확인한다. 실행 중에는 새 녹화기를 띄우지 않는다. [PowerShell 예제](사용가이드.md#녹화창-열기)

**등록된 업무의 실행 요청**에는 해당 업무의 `scripts/run.py --summary`를 사용한다. 필수 변수만 `--set "이름=값"`으로 전달한다. 실제 마우스나 키보드가 필요하다는 것을 이미 알면 창과 동작을 말하고 먼저 승인을 받는다. 위치 보정을 위한 창 캡처도 필요할 수 있으면 같이 설명한다. 이번 실행에 사용자가 승인한 경우만 `--allow-physical`을 붙인다. 접근성만 사용하는 업무에는 승인 질문이 필요 없다. 입력 방식이 불명확하면 실행기의 승인 요청에 응답한다.

첫 업무 입력 전에 실행기가 대상 창의 최상위 UIA 요소를 읽을 수 있는지 한 번 확인한다. 읽을 수 있으면 같은 호출에서 각 단계의 실제 대상을 확인하며 실행한다. 실패하면 첫 업무 입력 전에 멈추고 이유를 보고한다. 별도 `windows`, 전체 `--read-only`, `--input-plan`, 수동 전면화는 일반 실행 절차에서 생략한다. 결과의 `readability_check.status`는 창 확인 상태이고 범위는 `scope=window_root`다. 각 동작의 결과는 `steps`에서 확인한다. 마지막 파일 검증이 성공하면 `verified_outputs`에 있는 경로를 보고한다. 파일 내용을 검토해 달라는 요청이 있을 때 그 파일을 연다.

**처음 등록할 때** `register`가 현재 대상의 읽기 검사를 수행한다. 결과 폴더를 모르면 `scripts/python_workflow.py discover-output --exe "<실행 파일명>" --window "<창 제목>"`으로 해당 앱 주변의 로컬 출력 폴더 후보를 확인한다. 확인한 경로를 실행안에 보관한다. 후보가 모호하면 저장 경로를 좁힐 단서를 확인한다. 드라이브 전체 검색과 확인용 재내보내기는 생략한다.

**녹화를 저장하면** 저장 응답에서 준비된 실행용 작업을 사용한다. 이전 녹화나 미완성 초안은 `scripts/desktop_select.py recover --task "<원본>" --prepare`로 현재 창에 한 번 대조한다. 응답이 실행용 사본과 실행안을 제공하면 그 이름으로 진행한다. 별도 보완이 필요할 때만 응답의 해당 단계와 현재 창 단서를 읽는다. 결과 표를 우클릭하고 각 메뉴 이름을 한 단계씩 적은 녹화도 이 절차로 다룬다.

**첫 시험에서 보정할 때** 재사용할 작업은 실행용 사본을 `python_workflow.py register --task "<실행용 이름>" --out "<프로젝트의 새 업무 스킬 폴더>"`로 등록하고 그 폴더의 `scripts/run.py`로 시험한다. 응답에 `menu_repair.ticket`이 있으면 현재 작업의 입력과 결과를 유지한 채 [가이드의 보정 절차](사용가이드.md#첫-시험에서-우클릭-위치를-보정할-때)를 따른다. 승인 범위에서 현재 프레임을 읽고 적절한 지점으로 재개한다. 성공 영수증과 등록본의 보정 결과를 확인한다. 임시 실행 파일 작성, 전체 조회 재실행, 재녹화 요구를 기본 복구 절차로 삼지 않는다. 아래 수동 바인딩은 자동 준비에 남은 항목에만 사용한다.

이름 없는 입력란은 녹화한 상위 영역과 상대 위치로 다시 찾고 기록한 값을 사용한다. `field-input`, `submit`, `choose-item` 단계가 있으면 준비된 실행안을 그대로 사용한다. SQL 조건, 경로와 일반 문자열을 문장 패턴에 맞춰 다시 쓰게 하지 않는다. 시연 후 닫힌 창은 실행 중 그 창을 여는 단계 뒤에서 확인한다. XLSX처럼 목록에서 고른 항목은 해당 선택 단계까지 실행하고 선택 상태를 읽어 확인한다.

1. `bindings_template.steps`의 후보를 실제 컨트롤의 역할, 표시 라벨, automation ID, 소유 창과 저장된 문장에 대조한다. 고정값은 `fixed`, 실행할 때 받을 변수는 `required`, 버튼 호출은 `recorded`다. “내보내기 > 현재 시트 버튼 눌러줘”처럼 한 문장에 들어 있는 경로는 우클릭 단계의 `menu_binding_hint`에서 경로와 끝 단계(`through`)를 읽는다. 위치가 빠졌으면 해당 단계의 `image_args`로 표 내부 위치를 확인한다. 범위가 충돌하면 `conflicting_step`과 `recovery_hint`로 해당 단계만 대조한다. [복구 명령과 JSON 예시](사용가이드.md#저장한-녹화-이어서-실행하기)에 따라 `recover --task <원본> --bindings <JSON> --save-as <실행용 이름>`으로 사본을 만든다.
2. 표를 우클릭해 특정 메뉴를 고르라는 요청은 **해당 표와 메뉴 경로**를 실행한다. 같은 이름의 도구 모음 버튼으로 바꾸지 않는다. 실제 일반 녹화가 확보한 메뉴 경로나 표 위치를 우선 사용한다. 과거 녹화에 위치가 없으면 `recover --task <원본> --only <우클릭 단계> --image`로 현재 창의 로컬 이미지를 읽어 데이터 영역을 확인한다. `table` 외에 이름 있는 `group`이나 `custom`으로 노출된 표도 확인한다. 메뉴가 현재 닫혀 있으면 지정한 경로를 보존하고, 실제 재생 중 우클릭으로 열린 메뉴에서 부모와 하위를 순서대로 찾는다. 서로 다른 대화상자로 이어지는 클릭은 별도 단계로 유지한다.
3. 저장이나 준비 요청이면 원본을 보존한 실행안과 현재까지 확인한 대상을 보고한다. 이미 실행까지 요청받았으면 필요한 변수만 받아 같은 실행용 작업으로 이어간다. 입력 전송 후 결과가 불확실할 때는 방금 전송한 단계와 현재 화면 또는 산출물을 확인한다. 새로 열린 메뉴나 창은 그 시점의 소속과 대상을 확인하며 앞선 조회를 반복하지 않는다. 정보가 더 필요하면 현재 화면과 기록으로 해결되지 않은 한 가지를 구체적으로 묻는다.
4. 사용자가 보완 시연을 원하면 일반 작업에 `continue-recording --task <원본> --from-step <교체할 첫 단계>`를 쓴다. 이미 별도 녹화를 저장했으면 `--supplement <추가 녹화 이름>`으로 바로 합친다. 창이 떴다는 보고는 실제 창을 확인한 뒤에 한다. 반복 사용을 요청받으면 검증한 실행용 작업을 `python_workflow.py register --task <실행용 이름> --out <프로젝트>/.claude/skills/<업무 이름>`으로 등록한다.

예를 들어 “여기에 받은 품번 넣고 찾아줘”라면 녹화 위치 주변의 **품번** 라벨, 입력란, 조회 버튼을 현재 창에서 확인한다. 품번은 실행 때 받는 변수로, 조회는 별도의 버튼 동작으로 구성한다. 이름 있는 컨트롤은 `inspect`의 역할, 라벨, 상위 영역과 ID를 우선 사용한다. 연결한 대상과 값을 `instruct`로 저장하거나, 여러 동작을 직접 확인해 구성한 업무별 JSON을 `python_workflow.py register --recipe <파일> --out <업무 스킬 폴더>`로 등록할 수 있다. 원본 밖에 실행안을 만들 때에도 이후 단계의 작업 창, 분기, 고정값과 변수를 함께 옮긴다.

**같은 모양의 버튼이 목록에 반복될 때.** “A.로 시작하는 기기 켜 줘”에서는 `A.`가 행 이름의 앞부분이다. “위에서 두 번째 켜 줘”처럼 **현재 순서**를 지정한 문장에만 서수를 사용한다. `target_missing`, `visual_target_ambiguous`, `row_ordinal_not_visible`, `named_window_row_identity_required`가 나오면 관리창에서 해당 단계를 `ground`하고 현재 이미지를 읽는다. 화면의 행 이름 또는 ID와 **그 행 안에 있는 버튼**을 함께 식별한다. 녹화 뒤에 열린 창의 제목과 프로그램도 대조한다.

1. 그 행의 실행 버튼으로 새 창을 여는 단계에는 `desktop_select.py bind-row --task <원래 이름> --only <단계> --frame <이번 ground 영수증> --row-point <행 이름이나 ID의 X> <Y> --point <같은 행 버튼의 X> <Y>`를 사용한다. 두 지점 모두 방금 본 PNG 원본 기준이다. 이미 실행 중인 행도 같은 방식으로 식별할 수 있다. 연결 명령은 버튼을 누르지 않는다.
2. 대상 행이 더 있으면 같은 원본 녹화 이름으로 해당 단계의 `ground`와 `bind-row`를 반복한다. 이후 원래 이름으로 `plan`과 `replay`를 사용한다. 기존 조건 해석은 함께 유지된다. 재생에서는 행의 식별 표식과 정확한 기기창을 확인하고, 이미 열린 기기는 종료 버튼에 손대지 않고 다음 단계로 진행한다. 입력을 보냈는데 결과가 불확실하면 현재 창과 행의 상태부터 관찰한다.
3. 사용자가 반복 실행을 요청하면 `scripts/python_workflow.py register --task <녹화 이름> --out <프로젝트>/.claude/skills/<업무-이름>`으로 업무 스킬을 등록한다. 다음 요청에는 이 스킬의 `scripts/run.py`를 사용한다. 같은 행에서 편집하거나 값을 선택하는 업무는 해당 컨트롤의 역할과 동작을 확인해 `fill`, `select` 등으로 연결한다. 현재 화면의 정보만으로 두 후보를 구별할 수 없을 때만 두 이름을 제시해 묻는다. [같은 버튼이 여러 행에 보일 때](사용가이드.md#같은-버튼이-여러-행에-보일-때)

**조건이 포함된 녹화.** 사용자가 녹화 재생을 요청하면 `show`와 `plan`의 단계 원문, 작업 창, 후속 설명을 확인한다. `needs_review`나 `instruction_requires_structure`와 함께 `grounding_steps`가 오면 해당 단계의 실행안을 구성한다. 녹화 당시 알아보지 못한 요소가 있다는 이유로 앞 단계만 다시 녹화하도록 제안하지 않는다. “잠시 기다리고 광고가 있으면 닫고, 있든 없든 게임을 열어”는 **대기 → 광고가 있을 때만 닫기 → 게임 열기**다. 사용자가 마지막 동작을 양쪽 경우에 수행한다고 밝혔으면 다시 묻지 않는다. 두 창에 같은 문장이 있으면 각각의 창에 독립된 단계로 연결한다. [조건부 녹화 절차](사용가이드.md#조건이-섞인-문장을-녹화할-때)를 따른다.

1. 호스트가 직접 아래 형식의 JSON 파일을 작성한다. `number`는 원본 녹화 순번이고 `text`에는 사용자 설명 및 해당되는 후속 정정을 반영한다. 그림을 붙일 때는 같은 창의 동일 대상임을 확인한 녹화나 등록 스킬의 단계만 참조한다. 참조가 없으면 `from_skill`과 `from_step`을 생략한다. 복합 문장의 단일 화면 힌트를 광고와 최종 버튼 양쪽에 쓰지 않는다.

   ```json
   {"schema":1,"steps":[{"number":3,"text":"10초 대기. 광고가 있으면 광고 안의 X로 닫고, 두 경우 모두 게임 열기","seconds":10,"when_present":{"name":"광고"},"dismiss":{"name":"X"},"always":{"name":"포켓몬 카드 게임"}}]}
   ```

2. 대상 단계들을 한 파일에 넣고 `scripts/desktop_select.py interpret --task <원래 이름> --plan-file <로컬 JSON>`을 실행한다. 같은 이름으로 `replay --task <원래 이름> --exe <관리창 실행 파일> --window <관리창 제목>`을 호출한다. 설치가 두 곳이면 원본을 보여 준 설치본의 저장소와 같은지 `storage`로 확인한다. 해석에 필요한 자료를 사용자가 직접 만들게 하지 않는다.
3. 재생 또는 등록된 Python 업무 스킬이 `needs_scene`을 반환하면 호스트가 해당 영수증의 `image`를 로컬에서 읽는다. `condition`에서 광고가 보이면 광고 안의 닫기 지점을 `present`로, 광고가 없고 요청한 아이콘이 보이면 그 아이콘 지점을 `absent`로 제출한다. `scripts/python_workflow.py scene --ticket <이번 ticket> --decision present|absent --point X Y`를 사용하며 좌표는 해당 이미지 원본 크기 기준이다. 등록된 업무에서는 그 업무의 `scripts/run.py scene`에 같은 인자를 준다. 광고를 닫고 받은 `after_dismiss`의 새 이미지에 게임 아이콘이 보이고 광고가 사라졌으면 새 티켓에 `absent`와 아이콘 지점을 보낸다. 장면을 판별할 수 없으면 `--decision unknown`으로 종료한다. 대기 중에는 같은 실행을 이어가고, 티켓 만료나 전달 불확실 시에는 어느 단계까지 입력이 갔는지와 현재 화면을 먼저 확인한다.

**사용자가 녹화 실행을 요청하면 설명의 대상을 직접 찾는다.** 원문과 작업 창은 `show` 및 `plan`, 현재 화면은 `recover`로 확인한다. 필드와 버튼은 `bindings_template`에서 시작해 현재 컨트롤에 연결한다. 이미 확인한 일반 작업의 단일 지시는 `instruct`로도 편집할 수 있다. 그림 버튼이나 아이콘은 다음 순서로 연결한다.

1. `replay`가 `needs_grounding`을 반환하면 `grounding_steps`의 원문과 창을 사용한다. 의미가 명확한 버튼은 현재 화면의 정확한 이름을 먼저 찾는다. 이름 검색이 실패하면 `ground --task <작업> --only <원본 단계>`를 호출하고 반환된 로컬 `image`를 읽는다. 원래 지정한 프로그램/창의 이미지만 사용하고 외부 서비스로 전송하지 않는다.
2. 창에 한 번만 나타나는 아이콘은 원본 크기 이미지에서 중앙을 골라 `bind-visual --task <작업> --only <단계> --frame <영수증> --point X Y --save-as <새 작업명>`으로 연결한다. 두 명령은 클릭하지 않는다. 여러 단계면 **방금 만든 작업**에서 다음 단계를 연결한다. 같은 ▶가 반복되면 위의 행 이름과 버튼을 함께 식별하는 절차를 사용한다. 창이 닫혀 있으면 저장된 창 열기 동작과 사용자의 실행 요청 범위를 확인한다. `replay --only <원본 단계>`로 필요한 열기 동작만 실행할 수 있다. 이미 전달된 동작을 다시 보내기 전에 영수증과 현재 상태를 확인한다.
3. 준비된 작업을 `replay` 또는 Python 등록으로 이어간다. `visual_click_dispatched`는 클릭 전달을 뜻한다. 사용자가 앱 실행 확인을 원하면 해당 단계의 `ground`로 새 화면을 읽어 앱 이름이나 시작 화면까지 확인한다. 창이 달라졌거나 화면에 후보가 여럿일 때는 모호한 지점만 질문한다.

**여러 창에 걸친 녹화와 재생.** 녹화를 시작하면 첫 동작 전에도 **열린 창 선택**을 열 수 있다. 이미 열려 있는 기기창은 기본 목록에서 제목을 고르고 **이 창 선택**을 누른다. 별도 앱은 **다른 프로그램의 창도 보기**를 켜고 선택한다. 새 창이 방금 열렸으면 **새로 고침**을 누른다. 녹화한 동작으로 열린 관련 창이 앞으로 오면 녹화기가 자동으로 연결한다. 원래 창으로 돌아와 작업을 이어갈 수 있다. 단계의 창 정보는 자연어 편집, 저장, 재생, Python 등록에 함께 전달한다. 같은 프로그램에 같은 제목의 창이 여러 개면 사용자에게 구별할 제목을 요청한다. 하위 앱 내부 버튼은 실제로 인식하거나 상태 변화를 확인한 범위에서만 결과를 보고한다.

**입력 방식을 물어보면** 저장된 작업의 `replay ... --input-plan` 또는 등록된 Python 업무 스킬의 `scripts/run.py --input-plan`으로 각 단계의 입력 방식을 보여 준다. 업무 앱이 실행 중이지 않거나 필수 변수값이 없어도 확인할 수 있다. 창을 관찰하거나 앞으로 가져오거나 입력하지 않는다. 실행할 동작을 저장하는 `plan --task`와 구분하며, 이 결과를 현재 대상 식별이나 업무 실행 성공으로 보고하지 않는다.

**사용자 마우스와 키보드를 사용하지 않는 실행.** 사용자가 다른 업무를 계속하면서 실행하려는 경우 `select`, `fill`, `open`, `replay` 또는 등록된 Python `run.py`에 `--background-only`를 지정한다. 요청한 전체 단계에 표 우클릭, Enter 제출(`submit`), 위치 기반 대상(`anchor`), 행 버튼처럼 물리 입력이나 전면화가 필요한 단계가 있으면 첫 입력 전에 작업 전체를 차단한다. 일반 UIA 단계만 먼저 실행하지 않는다. 이 모드는 도구의 물리 입력, 창 전면화와 최소화 복원을 금지한다. 실제 조작에 쓰는 UIA 클라이언트의 `AutoSetFocus`도 `False`로 설정하고, 같은 클라이언트에서 설정값을 다시 읽어 확인한 뒤 조작한다. UIA 호출만 쓴다는 이유로 자동 포커스 이동이 없다고 단정하지 않는다. 앱이 호출에 반응해 스스로 창이나 대화상자를 앞으로 가져오는 것까지 보장하지는 않는다. 대상이 최소화되었거나 지원 근거가 없으면 현재 상태와 이유를 알리고 중지한다. 옵션을 생략하면 UIA의 자동 포커스 설정을 포함한 기존 실행 방식을 유지한다. 자세한 예시는 [입력 방식 안내](사용가이드.md#마우스와-키보드를-계속-쓰면서-실행하려면)를 따른다.

0.4.10은 목록 안 버튼의 일반 녹화, 실행 순번이 담긴 문장, 미인식 단계의 직접 편집을 지원한다. 0.4.9는 입력 방식을 실행 전에 확인하는 `--input-plan`과 도구의 물리 입력, 전면화, UIA 자동 포커스를 제한하는 `--background-only`를 추가한다. 기존 Python 실행안의 표 우클릭 메뉴, 같은 업무 창의 내보내기 대화상자, Enter로 조건 적용, Excel 파일 확인은 유지한다. 이름 없는 입력란은 현재 다시 찾은 상위 영역과 시연 위치로 식별할 수 있다. 콤보와 일반 입력란의 고정값/변수, 0.4.0 기반 실행기와 프로젝트별 저장, 녹화 설명 초안도 유지한다. 지금 한 번 조작하는 요청은 `scripts/desktop_select.py`의 콤보 `select`, 일반 입력란 `fill`, 버튼/메뉴 `open`을 사용한다. 호환되는 전체 녹화의 `replay`는 저장한 실행안을 사용한다. 기존 CUA MCP와 드라이버에 의존하지 않으며 ZIP은 소스와 문서만 포함한다.

**프로젝트별 저장.** `<프로젝트>/.claude/skills/desktop-select`에 설치하면 녹화는 `<프로젝트>/.desktop-select/tasks`, 실행안은 그 아래 `execution-plans`에 저장한다. 현재 명령 실행 폴더가 아니라 설치 위치를 기준으로 찾는다. 처음 사용할 때 `storage`로 실제 경로를 읽는다. 이 명령은 폴더를 만들거나 화면에 입력하지 않는다. 일반 위치에서 ZIP만 풀어 실행하면 풀어 놓은 `desktop-select` 안의 `.desktop-select/tasks`를 사용한다. 기존 공용 녹화를 자동으로 읽거나 가져오거나 삭제하지 않는다.

사용자가 공용 또는 별도 저장소를 지정했을 때만 해당 실행 환경의 `DESKTOP_SELECT_TASK_DIR`에 로컬 절대경로를 설정한다. 사용자 홈의 `.claude/skills`에 전역 설치한 경우에는 프로젝트로 간주하지 않고 명시적인 저장 경로를 요구한다. 사용자의 전역 환경변수나 시스템 설정을 변경하지 않는다. `storage`로 선택한 경로를 확인한 뒤 작업한다. 생성하는 Python 업무 스킬의 `register --out` 위치는 이 저장소와 별개이며 기존처럼 desktop-select와 같은 skills 폴더에 둔다. 프로젝트를 Git에 올릴 때 `.desktop-select/`의 업무 데이터가 함께 게시되지 않도록 사용자가 제외 설정을 확인하게 한다.

**녹화 초안과 미인식 복구.** 확인된 라벨과 버튼 이름으로 설명 초안을 채운다. 값을 읽지 못한 콤보와 일반 입력란에는 값을 추측하지 않고 필수 입력 변수 초안을 넣는다. 사용자가 수정하지 않은 초안도 저장한다. 녹화에서 대상만 못 찾은 단계에는 “MES Setup 조건을 N으로 해줘” 또는 “입력받은 변수를 Search 입력란에 입력해줘”처럼 대상 이름과 동작을 적을 수 있다. 이 단계는 `match=query`로 저장하며 실행할 때 직접 명령과 같은 현재 라벨/이름 탐색으로 대상을 찾는다. 임시 ref, 오래된 ID와 좌표를 재사용하지 않는다. 해당 창에 일치하는 대상이 하나면 원래 실행기로 조작한다. 현재 대상이 없거나 둘 이상이면 단계 번호와 이유를 알린다.

**자유문장 처리.** 편집용 초안의 단계별 문장과 일반 작업의 `instruction_draft`를 호스트가 읽는다. 현재 표시 라벨, ID나 이름으로 대상을 확인하면 실행용 사본을 만든다. `bindings_template.steps`에는 현재 확인된 후보만 들어 있다. 미확정 단계에 현재 표의 이미지나 메뉴 계층이 필요한지 확인하고 실행 중 열리는 소유 창은 열린 시점에 관찰한다.

**문장은 등록 시 한 번 해석한다.** 편집용 초안과 일반 작업 모두 `recover --task <이름>`으로 현재 창에서 대상을 확인하고 구조화한다. 이미 일반 작업으로 저장된 한 단계를 편집하려면 `instruct --task <이름> --only <번호> --text <원문> --mode fixed|required|recorded --save-as <새 작업명>`을 쓸 수 있다. 필드에는 `--argument <값 또는 변수명>`을 더한다. `plan`으로 실행안 상태를 확인한다.

`plan --task <이름>`은 현재 지시를 실행안으로 저장한다. 녹화 때 확인됐거나 `recover`로 보완한 `result-menu`도 컴파일한다. 호환되는 전체 작업은 필수 값이 채워지면 `replay`로 빠르게 실행한다. 미해결 단계가 있으면 해당 단계의 `live_recovery`를 확인한다.

실패한 녹화 단계를 수정할 때는 결과의 `source_stopped_at` 또는 각 항목의 `source_step`을 사용한다. 실행안에는 대기가 별도 단계로 들어가 실행 순번과 원래 녹화 순번이 다를 수 있다.

**조회 뒤 대기는 명시한다.** 비동기 조회 후 내보내려면 최초 등록 때 사용자가 정한 대기 또는 기존 결과 확인 조건을 저장한다. 예를 들어 `instruct ... --only 3 --text "조회한 뒤 5초 기다려" --mode recorded --wait-after 5 --save-as <새 이름>`은 버튼 뒤 5초 대기를 넣는다. 대기를 지정하지 않은 중간 버튼은 기존 재생처럼 전달 확인에서 멈춘다. 고정 대기는 업무 결과를 검증하지 않는다. 창 상태와 결과에 맞지 않는 시간을 임의로 추가하지 않는다.

**빠른 반복 실행.** 호스트가 각 필드의 fixed/required 지시, 조회 대기, 표의 메뉴 경로를 보완하고 `plan`을 확인한다. 준비된 작업은 `scripts/python_workflow.py register --task <이름> --out <같은 skills 폴더의 새 업무 스킬>`로 등록한다. `source-task.json`에 실행용 녹화, `workflow.json`에 동작, `scripts/run.py`에 실행 진입점을 저장한다. 후속 저장 대화상자나 파일 확인을 더하려면 [사용 가이드](사용가이드.md)의 `register --recipe <파일>` 절차를 사용한다. 등록은 읽기 전용이다. 이후 업무 스킬의 `scripts/run.py --summary --set "Family=Hybrid"`로 실행한다. 실행 때 받을 필수 값이 빠졌으면 첫 입력 전에 필요한 값만 묻는다.

**대화상자와 이름 기반 대상.** 표준 Windows 대화상자(`#32770`)의 창 외곽이 `IsPassword=None`을 반환하면 실제 최상위 HWND, 프로세스, 클래스, 현재 UIA 요소와 편집 기능 부재를 확인한 경우에만 내부를 탐색한다. 명시적으로 보호되었거나 보호 여부를 알 수 없는 입력 컨트롤은 계속 차단한다. 숫자 ID가 제외되어 `match=name`으로 녹화된 대상도 등록할 수 있다. 현재 업무 창에서 정확한 이름과 역할로 조회한 뒤 저장한 상위 영역을 대조한다. 후보가 없거나 여럿이면 입력하지 않는다. 이름 변경을 추측하거나 숫자 ID/옛 좌표로 대체하지 않는다.

**조회부터 저장 대화상자까지 한 실행안으로 연결하기.** 현재 화면에서 확인한 순서를 literal recipe로 작성해 `python_workflow.py register --recipe <파일> --out <업무 스킬>`로 등록한다. `context-menu`는 가르친 표의 상대 위치에서 우클릭하고 지정 메뉴 경로를 따라간다. 뒤의 `set-value`와 `invoke`에 `popup: {"title": "정확한 대화상자 제목", "timeout": 3}`을 붙이면 해당 업무 창에 속한 팝업이 하나 나타날 때만 진행한다. 필터 입력 후 Enter가 필요한 앱은 별도의 `submit` 단계로 입력란에 Enter 한 번을 보낸다. 마지막 `verify-file`은 모든 입력 전의 파일 상태와 비교해 새로 생성되거나 변경된 로컬 `.xlsx`/`.xlsm` 구조를 확인한다. 셀 내용과 조회 결과의 정확성을 검증한 것은 아니다. 자세한 형식은 [사용 가이드의 내보내기 실행안](사용가이드.md#조회-우클릭-내보내기-창을-python-실행안으로-연결하기)을 읽는다.

등록과 `--read-only`는 팝업을 열거나 입력하지 않는다. 아직 열리지 않은 팝업 단계는 `pending_scopes`와 `deferred`로 남는다. 등록 완료를 팝업의 실제 동작 검증 완료로 보고하지 않는다. 실행 때 팝업이 없거나 여럿이거나 소속이 다르면 중단한다. 녹화한 `result-menu`는 업무 스킬 등록 시 같은 순서로 컴파일한다. 과거의 미해결 우클릭과 메뉴 항목은 위의 `recover`로 연결한 뒤 등록한다.

**이름 없는 입력란.** 정확한 ID나 이름이 있으면 그것을 우선한다. 없으면 `selector`에 `anchor`(현재 고유한 상위 영역의 ID/이름과 역할), `point`(그 영역 안의 상대 위치), `role`, `class_name`을 기록할 수 있다. 실행 때 상위 영역을 다시 찾고 그 위치의 UIA 대상이 역할, 클래스, 소유관계, 보호 여부, 표시 영역과 일치하는지 확인한다. 저장한 숫자 HWND나 절대 화면 좌표는 쓰지 않으며 임의 좌표 클릭으로 전환하지 않는다. 이 방식은 화면이 보여야 하고 대상 창을 앞으로 가져온다. 표 우클릭은 실제 마우스, `submit`은 실제 키보드를 사용하므로 그 단계 중에는 마우스와 키보드를 사용하지 않도록 알린다. 일반 ValuePattern/Invoke 단계는 접근성 호출을 유지한다.

**일반 입력란.** `fill --target <입력란> --value <문자열>`은 보호되지 않은 쓰기 가능한 textfield의 값을 한 번 설정하고 현재 값을 정확히 다시 읽는다. 따옴표, 한글, 앞자리 0을 그대로 보존한다. 명시적인 빈 문자열 `--value=` 또는 변수 `--set "SearchText="`는 입력란을 비운다. 콤보의 빈 값은 실행 시작 전에 차단한다. 비밀번호 입력과 콤보 내부 편집 피어를 별도 입력란으로 취급하지 않으며, 지원하지 않는 위젯에 키 입력이나 클립보드 방식으로 전환하지 않는다.

**쓰기 가능한 콤보.** `select`의 값은 해당 컨트롤에 넣을 실제 문자열이다. 부모 콤보가 SetValue를 지원하면 옵션 펼치기나 항목 Select 없이 한 번 쓰고 현재 값을 다시 읽는다. 표시 이름과 내부 코드가 다른 컨트롤은 현재 제공자 값 또는 사용자가 지정한 코드를 쓴다. 동일한 편집 피어들이 같은 값을 보여 주면 일치 근거로 인정한다. 서로 다른 값이면 성공으로 처리하지 않으며 재입력하지 않는다. SetValue가 없는 콤보만 기존 항목 선택 경로를 쓴다.

**등록된 업무 없이 창을 직접 조작할 때**

1. `windows --exe <프로그램.exe>`로 업무 창을 찾는다. MenuAgent의 실행 파일 이름은 로컬 PowerShell에서 `Get-Process -Name '*MenuAgent*' | Select-Object -ExpandProperty ProcessName -Unique`로 확인하고 `.exe`를 붙인다. 사용자가 지목한 업무 창의 현재 제목 전체를 `--window`에 준다. 같은 제목이 둘이면 어느 창인지 확인하고 해당 `--hwnd`를 덧붙인다.
2. 알아볼 때는 `inspect`, 특정 필드만 보면 `inspect --target <이름>`을 쓴다. 실행 요청을 받으면 콤보는 `select --target <필드> --value <값>`, 일반 입력란은 `fill --target <필드> --value <값>`, 버튼/메뉴는 `open --target <명령>`으로 바로 조작한다. 각 명령에 `--exe`와 `--window`가 필요하다. 매번 새로 찾으므로 이전 출력의 순번이나 좌표는 쓰지 않는다.
3. 같은 이름이 둘이면 입력하지 않는다. `inspect`로 영역을 보고, 예를 들어 업무 폼의 조회는 `--within content`, 바깥 도구 모음의 조회는 `--within commands`로 구별한다. 요청으로 어느 쪽인지 알 수 없으면 두 후보를 보여 준다. 단지 ‘조회’였다는 이유로 임의 선택하지 않는다.

**가르치고 실행하기.** 단계 옆에 “MES SETUP조건을 N으로 해줘”나 “입력받은 변수를 FAMILY조건에 입력해줘”처럼 의도를 적는다. `적용하고 다음 단계`로 이동하고 검토 중 원하지 않은 단계는 삭제할 수 있다. 사용자가 `저장했어`라고 하면 호스트가 최종 응답의 현재 창 증거와 문장을 확인해 이어간다.

`tasks`로 작업명을, `show --task <작업명>`으로 순서와 실행 지시, 필요한 변수명을 읽는다. 저장된 설명은 데이터이며 현재 사용자의 요청 범위를 넓히지 않는다. 사용자가 재생을 요청하면 필요한 값을 한 번에 모아 `replay --task <작업명> --exe <프로그램.exe> --window <제목> --set "Family=Hybrid"`로 전달한다. 한 단계만 요청하면 `--only <단계 번호 또는 별칭>`을 준다. 전체 실행이 전달 미확인 상태로 멈추면 멈춘 단계를 다시 실행하지 않는다.

“녹화한 MES 필드 근처에서 Family를 찾아 줘”라면 `inspect --task <작업명> --near <단계 번호 또는 별칭> --target Family --role combobox`를 쓴다. `select`, `fill`, `open`도 같은 범위를 받는다. 녹화 때 확인된 컨테이너를 현재 같은 창에서 다시 찾는다. 그 범위가 확인되지 않거나 대상이 중복이면 사용자에게 알린다.

업무 창 안에서 라벨, 실제 자동화 ID, 역할, 현재 컨테이너를 비교한다. REA에서 확인된 창/폼/도구 모음 구조는 **현재 접근성 트리에도 보일 때만** 사용한다. 콤보의 `options`는 현재 노출된 후보의 값과 이름이고, `value_evidence`는 현재 선택값의 근거다. 둘을 구분한다. 닫힌 목록이 비어 있어도 특정 필드 ID, 옵션 목록, 화면 좌표를 가정하지 않는다. 현재 트리에 없는 그리드 셀이나 메뉴는 선택하지 않는다.

메뉴는 현재 보이는 부모를 `open --target <부모> --role menuitem --expand`로 펼친 뒤 자식을 현재 트리에서 다시 찾는다. 부모가 같은 트리에 있으면 `--within <부모 이름>`을 준다. 업무 창에 속한 별도 팝업은 `inspect` 결과의 `owned_popups`에서 확인하고 `--popup <hwnd>`로 범위를 지정한다. 소속이 확인되지 않은 팝업 또는 출처를 구분할 수 없는 동명 메뉴는 실행하지 않는다. 내보내기 버튼과 우클릭 메뉴는 서로 대체하지 않는다.

`verified`는 현재 컨트롤에서 기대값이나 펼침/선택 상태를 다시 읽었다는 뜻이다. `delivered_unverified`는 전달됐지만 결과를 확인할 수 없다는 뜻이다. 조회 결과 생성이나 업무 저장 완료와 구분한다. 확인되지 않은 입력을 반복하거나 물리 클릭으로 전환하지 않는다. 여러 필드를 연달아 요청받으면 각 필드가 확인된 다음에만 다음 조작을 한다.

**목록의 행을 실행해 달라는 요청.** 사용자가 “첫번째 요소 실행버튼 누르기”처럼 현재 목록의 순번을 명시하면 `row-launch --exe <프로그램.exe> --window <제목> --ordinal 1 --preview`로 현재 보이는 행과 버튼을 입력 없이 확인한다. 사용자가 실제 실행을 요청할 때 `--preview`를 빼고 한 번 수행한다. 실행 확인의 범위는 같은 행의 버튼과 상태 변화다. 비정형 문장이 초안에 남으면 호스트가 의도와 순번을 확인해 `instruct --task <이름> --only <단계> --text <사용자 원문> --row <순번> --save-as <새 이름>`으로 구조화하고 원문을 보존한다. 사용자가 문법을 다시 작성하도록 요구하지 않는다. 별칭에만 실행 문장이 남은 옛 미인식 단계는 지원하는 표현이면 읽을 때 복구한다. 안내문만 남은 단계는 임의로 실행하지 않는다.

**행 표식과 완료 상태를 직접 지정할 때**는 검토 화면의 ‘행 버튼으로 지정’ 또는 ‘단계 추가 → 행 버튼 가르치기’를 사용한다. 사용자가 한 행 안에서 고유한 번호나 이름, 클릭할 버튼, 실행 상태가 표시되는 부분을 각각 지정한다. 사용자가 버튼을 시연하고 화면에 원하는 최종 상태가 나타나면 같은 위치의 완료 표시를 기록한다. 숫자나 이름은 목록 순서가 바뀌어도 같은 항목을 식별할 수 있어야 한다. 이 방식은 시연한 항목을 따라간다. 현재 보이는 상위 세 행을 매번 고르는 지시는 순번을 쓰는 행 실행으로 저장한다.

이 단계의 재생은 실제 마우스를 사용한다. 창을 표시하고 버튼이 있는 행을 보이게 한다. 같은 행의 완료 표시가 이미 보이면 입력 없이 확인한다. 입력 뒤 상태를 확인할 수 없으면 읽기 전용 `row-status --task <작업명> --exe <프로그램.exe> --window <제목>`으로 다시 확인한다. 완료 근거는 가르친 행의 상태 표시다. 화면에서 읽을 수 있는 고유 표시나 완료 표시가 없는 행에는 이 방식을 적용할 수 없다.

**조회 후 표 우클릭과 Excel 내보내기.** 일반 녹화에서 사용자가 결과를 우클릭하고 실제 메뉴를 차례로 선택하면 해당 영역과 경로를 사용한다. 이전 녹화에서 위치가 빠진 경우 `recover --task <이름> --only <단계> --image`로 현재 표의 데이터 지점을 확인하고 이어지는 메뉴 클릭을 같은 경로로 묶는다. 실행 시 방금 열린 메뉴의 소유자와 계층을 확인한다. 조회 완료를 상태 글자나 표 안의 표시로 판별하려면 ‘단계 추가 → 조회 후 우클릭 메뉴 가르치기’에서 완료 조건도 정할 수 있다. 조회 버튼은 한 번만 실행한다.

파일 생성까지 확인하려면 업무 앱이 실제로 쓰는 로컬 파일 경로나 전용 폴더를 확인한다. 저장 대화상자 조작을 요청받으면 별도 Python 실행안에 현재 확인한 팝업 단계와 경로를 넣는다. 메뉴 전달, 파일 생성, 데이터 내용 중 실제로 확인한 범위까지 보고한다. 전달이 불확실하면 현재 창과 파일을 먼저 확인한다.

설치, 회사 PC에서 처음 해 볼 요청, 결과별 대응은 [시작 안내](사용가이드.md)를 참고한다.

실제 앱 시험 범위와 측정 기록은 [0.4.8 검증 문서](https://github.com/bongG-moon/agent-desktop-workflows/blob/desktop-select-v0.4.8/docs/desktop-select-048-validation.md)를 참고한다. 회사 FX 제공자의 동작을 이 PC의 시험으로 확인했다고 말하지 않는다.
