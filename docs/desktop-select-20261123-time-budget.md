# Desktop Select 대기 시간과 모델 입력량 검증

2026-11-23, 0.4.27 기반으로 검증한 수정본이며 아래 변경을 0.4.28 배포에 포함한다. 회사 FX 화면 대신 격리한 Windows 시험 앱에서 실제 Claude Code를 실행했다. 개인 설정, 모델 선택, 플러그인과 기존 후크를 변경하지 않았다. 원격 모델 응답 시간과 엔진 실행 시간을 나누어 기록한다. 전체 변경은 [0.4.28 릴리스 노트](desktop-select-v0.4.28-release.md)에 정리했다.

## 중복 작업 수정

- 기본 SKILL.md는 실행 경로를 먼저 보여주고 세부 복구 설명은 참조 문서에 둔다. 4,723자 / UTF-8 9,189바이트에서 3,407자 / 6,223바이트로 줄였다. 바이트 기준 32.3% 감소이며 토큰 감소율과 같은 의미는 아니다.
- 원본 녹화와 컴파일한 실행안의 값, 동작, 창과 구체적 대상이 정확히 일치하면 등록 시 전체 읽기 검사를 반복하지 않는다. 등록 후 실행에서 현재 요소 확인은 유지한다. 모호한 query와 원본 없는 레시피는 사전 검사를 유지한다.
- register --task --run은 위 조건에서 등록 전용 프로세스를 만들지 않고 실제 실행 프로세스를 한 번 시작한다. 회귀 검사에서 엔진 호출 2회에서 1회, 등록 전용 프로세스 1회에서 0회로 확인했다.
- 현재 결과 행을 열라는 지시에는 입력값 비교를 임의로 추가하지 않는다. 생성 업무 안내도 값 비교 방식과 현재 행 방식으로 구분했다. 대표 안내는 2,884에서 2,603 UTF-8바이트로 줄었다.
- 결과를 이미지로 확인해야 할 때 이미지 해시와 동일 여부를 반환한다. 이미 본 동일 이미지의 모델 재열람을 생략하도록 안내한다. 앱은 입력 없이도 갱신될 수 있어 현재 화면 검증용 로컬 캡처는 유지한다. 유효기간과 원본 업무 값은 줄이거나 바꾸지 않는다.
- 녹화 응답의 ASCII 이스케이프는 유지한다. Windows PowerShell의 CP949 경로에서 한글 손상을 막는 기존 호환 장치이며 실제 무입력 시험에서도 필요성을 확인했다.

## 녹화 시작

로컬 새 Python 프로세스 7회 중앙값은 빈 Python 0.0967초, 녹화 모듈 로드 0.1859초, storage 명령 0.1996초였다. 현재 창 메타데이터 9개를 읽는 데는 중앙값 0.00079초가 걸렸고 UIA 세션을 만들지 않았다. 같은 PID의 프로세스 정보를 반복해서 읽지 않았다. 준비 응답은 50ms마다 확인하며 준비되면 바로 반환한다. 8초를 항상 기다리는 방식은 아니다.

| 실제 Claude Code 측정 | 변경 전 안내 | 간결한 안내 |
|---|---:|---:|
| 사용자 요청에서 녹화창 준비까지 | 8.052초 | 8.518초 |
| 요청에서 최종 응답까지 | 20.433초 | 19.442초 |
| 공개 녹화 명령 호출 | 1 | 1 |
| 도움말 / 소스 검색 | 0 / 0 | 0 / 0 |
| Claude API 처리 시간 | 11.719초 | 10.447초 |
| 캐시 생성 입력 토큰 | 34,679 | 31,905 |
| 캐시 읽기 입력 토큰 | 217,250 | 219,264 |
| 일반 입력 / 출력 토큰 | 10 / 1,176 | 10 / 1,115 |

실제 CLI가 보고한 누적 토큰이다. 초기 컨텍스트, 모든 모델 왕복과 기존 플러그인까지 포함하며 현재 스킬의 토큰만 뜻하지 않는다. 시작 비교는 메뉴 재개 안내 한 문단을 추가하기 전의 간결안(3,187자 / 5,803바이트)으로 수행했다. 각 버전을 한 번씩 측정했으므로 인과적인 속도 개선율이나 안정적인 토큰 절감률로 해석하지 않는다. 시작 속도는 이 측정에서 개선됐다고 볼 수 없다.

두 실행 모두 Skill 호출과 녹화 명령 뒤 기존 Company Agent의 검증 기록 명령이 한 번 더 요청됐다. 이 명령은 업무와 무관한 사용자 상태 기록이므로 합성 시험의 허용 범위에서 거절됐다. 녹화창은 그 전에 준비됐다. 해당 후크가 없는 회사 환경에 이 추가 호출을 적용하거나 후크의 비용을 엔진 비용이라고 보고하지 않는다. 사용자 설정 해시는 시험 전후 같았다.

첫 준비 시험 한 건은 모델이 앱 힌트를 축약한 것을 하네스의 정확한 문자열 허용 목록이 거절했다. 이 결과는 시작 성능 비교에서 제외했다. 비교 시험은 동일한 짧은 앱 힌트로 수행했다. 하네스는 실제 프로그램 이름이나 사용자의 데이터에 대한 조작을 허용하지 않는다.

증거는 `.build/time-budget-20261123/start-before-valid/summary.json`, `start-after/summary.json`, `.build/current-result-20261123/startup-audit.json`에 있다.

## 저장한 녹화의 첫 시험

전체 경로 검토 중 try-recording의 메뉴 위치 실패가 등록 업무의 기존 메뉴 보정 티켓과 연결되지 않은 공백을 발견했다. 첫 시험 명령의 반복은 동일한 실패 영수증만 돌려주므로 이를 해결하려고 조회를 다시 하거나 소스를 탐색하면 지연이 커진다. 실제 Claude Code에서도 이 공백을 재현했다. 모델은 소스 조사 없이 try-recording을 먼저 호출했고 요청에서 첫 입력까지 11.506초, 준비 0.105초, 실행 2.230초가 걸렸다. 조회 1회 후 위치 오류로 중단했으나 menu_repair와 재개 인자가 없어 안내 읽기와 검색으로 돌아갔다. 합성 시험 하네스는 발급된 재개 경로 이외의 새 recover --image 호출을 거절했으므로, 이후 기존 버전의 복구 가능성 전체를 측정한 결과는 아니다. 첫 시험에서 재개 계약이 없었던 사실과 추가 탐색은 실제 응답으로 확인했다.

메뉴가 있는 첫 시험은 기존 메뉴 재개 실행기를 같은 worker 안에서 사용하도록 연결했다. 메뉴 없는 경로는 그대로다. 최초 실행에서 추가 worker나 사전 UIA 검사는 만들지 않는다. 위치 실패 후 inspect-menu-trial / resume-menu-trial로 같은 조회 결과에서 이어간다. --auto-repair-frame은 화면 확인까지 허용한 경우에만 사용하며 실패한 메뉴 위치에서만 캡처한다.

보정한 위치는 원본 녹화를 보존한 실행용 사본에 반영한다. effective_task와 register_args가 그 사본을 가리킨다. 이미 전달이 불확실한 메뉴 입력은 재개 대상으로 만들지 않는다. 대기 삽입에 따른 단계 번호 변환, 관련 창 연결, 여러 메뉴 보정 누적, 같은 시험의 재호출에서 추가 조회 0회를 회귀로 확인했다.

## 전체 회귀와 배포 파일

전체 Windows 회귀 검사 1,378개가 70.568초에 통과했다. 마지막 검토에서 무입력 잠금 거절 뒤 같은 시험이 준비 폴더 충돌로 재시작되지 않는 경우도 수정했다. 원래 상태와 실행안이 같고 보정 티켓이나 재개 기록이 없는 준비 결과만 재사용한다. 최종 전체 회귀 검사 1,381개가 44.601초에 통과했다. 최종 로그는 `.build/time-budget-20261123/regression-final.log`다. 독립 검토에서 이름 없는 invoke의 빠른 등록이 기존 명령 이름 검사를 빠뜨리는 경우를 재현했고, 이름 증거가 없는 녹화는 기존 사전 확인을 유지하도록 수정했다. 정상적인 이름 증거 경로는 추가 확인 없이 등록된다.

이 검증에서 만든 0.4.27 로컬 ZIP의 64개 파일을 당시 정본과 바이트 비교했고 일치했다. 검증한 변경은 0.4.28 배포에 포함하며, 위 시간과 파일 수는 당시 로컬 검증의 기록이다.


## 실제 Claude Code의 보정과 반복 실행

수정본으로 새 격리 프로젝트에서 첫 시험과 위치 보정, 등록, 반복 실행을 완주했다. 실제 사람의 시연을 새로 녹화한 시험은 아니며, 현재 Windows 요소를 관찰해 녹화 스키마로 준비한 합성 기록이다. 업무 입력과 보정 결정, 실행 명령은 실제 설치된 Claude Code 모델이 수행했다. 하네스는 실제 발급된 재개 인자만 허용하고 시험 프로그램의 상태를 별도로 관찰했다.

| 사용자 요청 기준 시간과 횟수 | 첫 시험, 보정, 등록 | 등록 업무 재실행 |
|---|---:|---:|
| 첫 입력까지 | 11.546초 | 9.780초 |
| 파일 생성 검증 응답까지 | 27.195초 | 13.173초 |
| 스킬 등록 응답까지 | 32.272초 | 해당 없음 |
| 공개 실행 명령 | 3회 | 1회 |
| 모델의 이미지 확인 | 1회 | 0회 |
| 조회 / 우클릭 / 내보내기 | 1 / 1 / 1 | 1 / 1 / 1 |
| 잘못된 지점 클릭 | 0회 | 0회 |

첫 명령의 엔진 준비는 0.108초, 위치 오류까지의 실행은 2.497초, 보정 후 재개는 1.571초였다. 등록 업무 재실행은 엔진 준비 0.0999초, 전체 2.9668초였다. 모델 선택, 네트워크와 도구 반환 대기까지 포함한 위 표의 시간과 혼동하지 않는다.

첫 시험에서 보정한 지점이 새 실행용 사본 및 등록 레시피에 저장됐다. 원본 녹화는 바뀌지 않았다. 다음 실행은 같은 입력 조건에서 새로운 이미지나 위치 보정 없이 같은 저장 지점으로 끝났고, 출력 통합 문서의 조건과 조회 횟수 셀도 하네스에서 확인했다. 다른 입력값으로 바꾼 반복 실행의 모델 성능을 측정한 것은 아니다. 처음 실행은 표 관련 참조 문서를 한 번 읽었고, 등록 뒤 Glob 목록 조회도 한 번 있었다. 완전한 재개 인자와 등록 응답이 있으면 이 조회를 추가하지 않도록 최종 안내를 더 명확히 했다. 이 문구 보완 뒤 모델을 다시 실행하지 않았으므로 참조/Glob이 항상 0회라고 주장하지 않는다.

| CLI 보고 토큰 누적량 | 첫 시험, 보정, 등록 | 등록 업무 재실행 |
|---|---:|---:|
| 일반 입력 | 18 | 10 |
| 캐시 생성 입력 | 43,735 | 34,776 |
| 캐시 읽기 입력 | 447,436 | 217,647 |
| 출력 | 2,884 | 1,463 |

이 수치는 해당 개인 환경 전체를 포함한다. 실행 명령이 줄어도 기본 컨텍스트와 캐시 읽기가 각 모델 왕복마다 집계되므로 스킬 자체의 토큰 사용량이나 회사 환경의 비용으로 해석하지 않는다. 변경 전은 중간에 실패했고 변경 후는 등록까지 끝냈기 때문에 둘의 전체 토큰 차이로 절감률을 계산하지 않는다.

개인 Company Agent의 검증 기록 요청은 업무 완료 뒤 각 세션에 한 번 있었다. 합성 범위 밖의 기록이라 하네스에서 거절됐고 개인 설정은 그대로다. 첫 세션 최종 대화 종료는 요청 후 48.541초, 반복 세션은 23.931초로, 업무 완료 응답보다 늦다. 회사 환경에 이 후크가 없다면 이 특정 추가 호출은 없지만 회사 모델의 응답 지연까지 없어지는 것은 아니다.

최종 증거는 `.build/time-budget-20261123/workflow-host-fixed/recorded-benchmark.json`, 같은 폴더의 `phases.json`, `repeat/phases.json`, `verification.json`이다. GUI 시험 전 사용자 입력이 감지돼 합성 준비가 두 번 중단됐고, 입력을 비운 뒤 시험했다. 그 두 번에는 모델 요청이나 업무 조회가 없었다. 최종 잠금 재시도 보완은 실제 모델 시험 후 별도 회귀로 확인한 변경이다. 회사 FX의 성능과 실제 잠금 상태의 각 앱 지원은 이 결과로 보장하지 않는다.
