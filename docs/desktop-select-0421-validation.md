# Desktop Select 0.4.21 새 녹화 검증

2026-11-16에 Windows의 실제 DBeaver Community 26.2.4에서 새로 시연해 검증했습니다. SQLite의 가상 데이터 10행을 사용했고, 기존 녹화나 수동으로 작성한 실행안을 재사용하지 않았습니다. 최종 녹화가 만든 9단계 실행안을 그대로 등록해 첫 시험을 마쳤습니다. 별도 복사본에서는 잘못된 우클릭 위치를 넣어 보정과 다음 실행의 재사용도 확인했습니다.

## 이번에 해결한 문제

실제 녹화를 반복하면서 다음 결함을 확인하고 수정했습니다. 처음부터 모든 시험이 성공했던 것은 아닙니다.

| 발생한 문제 | 수정한 동작 |
| --- | --- |
| 이름 없는 필터와 Directory 입력란에서 대상이나 값이 빠짐 | 고유한 상위 영역, 내부 위치, 입력값을 함께 보존합니다. 문자열 안의 따옴표도 유지합니다. |
| Enter 뒤 화면이 갱신되면 직전 입력란을 다시 찾지 못함 | 키를 누르기 전에 확인한 입력란과 실제 키보드 포커스를 연결해 별도 적용 단계로 저장합니다. |
| Enter 단계를 포함한 초안 저장이 검증에서 거부됨 | 저장 형식에 적용 동작을 포함하고 다시 열어도 값을 유지하도록 수정했습니다. |
| 표의 임시 셀이나 팝업 항목 때문에 우클릭 영역이 불안정함 | 표의 지속되는 상위 영역과 실제 메뉴 선택을 한 단계로 연결합니다. |
| Export data로 열린 창이 더 오래된 클릭에 연결됨 | 같은 소속 창에서 확인한 가장 최근 메뉴 동작에 새 창을 연결합니다. |
| 시연 후 닫힌 Data Transfer 창 때문에 등록이 막힘 | 창을 여는 선행 단계가 확인됐으면 해당 창의 검사를 실제 실행 시점까지 미룹니다. |
| XLSX가 일반 클릭이나 미인식 단계로 남음 | 목록 항목 선택으로 저장하고 재생 시 선택 상태를 읽어 확인합니다. |
| Proceed 직후 창이 닫혀 마지막 입력값과 버튼이 사라짐 | 창이 살아 있을 때 확인한 값과 실제 클릭의 대상 정보를 보존합니다. |

녹화의 설명과 화면 힌트를 호스트 모델이 함께 해석하고, 현재 화면에서 확인된 대상을 실행안으로 연결합니다. 실행 중 위치가 달라지면 이미 보낸 입력을 반복하지 않고 해당 단계부터 보정합니다. 등록 후에는 기존 Python 실행 경로를 사용합니다. 추가 모델, 백그라운드 서비스, 의존 프로그램은 도입하지 않았습니다.

## 새 녹화의 첫 시험

시연 순서는 필터 입력 → Enter → 결과 표 우클릭 → Export data → XLSX 선택 → Next 세 번 → Directory 입력 → Proceed였습니다. 저장 후 생성된 설명 초안과 실행안을 사용했습니다. XLSX 선택이 이전 설정에 의존하지 않도록 첫 시험 전에 파일 형식을 CSV로 바꿔 두었습니다.

녹화 원본과 등록된 `source-task.json`은 같았고, 원본을 변환한 실행안도 등록된 `workflow.json`과 같았습니다. 사용자에게 문장을 다시 쓰거나 별도 녹화를 하도록 요청하지 않았고, 시험을 위해 녹화 파일이나 실행안을 수작업으로 고치지 않았습니다.

| 단계 | 실제 동작 | 엔진에서 측정한 시간 | 확인 결과 |
| --- | --- | ---: | --- |
| 1 | 필터에 `Status = 'N' AND Family = 'Hybrid'` 입력 | 1.800초 | 입력값 일치 |
| 2 | 같은 입력란에서 Enter | 1.573초 | 키 전달 확인 |
| 3 | 결과 표 우클릭 → Export data | 4.455초 | 메뉴 경로 실행 확인 |
| 4 | XLSX 선택 | 1.363초 | 선택 상태 일치 |
| 5 | Next | 0.403초 | 호출 전달 확인 |
| 6 | Next | 0.504초 | 호출 전달 확인 |
| 7 | Next | 0.502초 | 호출 전달 확인 |
| 8 | Directory 입력 | 1.027초 | 입력값 일치 |
| 9 | Proceed | 0.326초 | 호출 전달 확인 |

| 구간 | 실측 | 범위 |
| --- | ---: | --- |
| 첫 클릭부터 대상 기록까지 | 9.225초 | 이번 환경에서 여전히 느린 구간 |
| 등록과 대상 확인 | 3.466초 | 저장한 9단계로 업무 스킬 생성 |
| 등록 스킬의 첫 시험 | 12.439초 | 새 Python 프로세스 시작부터 결과 반환까지 |
| 첫 시험의 실행 전 읽기 검사 | 0.011초 | 최상위 창 한 번, 위 첫 시험 시간에 포함 |

단계별 시간은 엔진 내부 측정이고 전체 시간은 프로세스 단위 측정이므로 단순 합계와 일치하지 않을 수 있습니다. 시연 전체에는 화면 관찰과 도구 호출 사이의 대기가 포함돼 실행 속도 비교 기준으로 사용하지 않았습니다. 이 수치는 해당 PC의 한 차례 실측이며 다른 앱이나 회사 PC의 속도를 보장하지 않습니다.

## 위치 보정과 다음 실행

정상 녹화의 첫 시험과 별도로, 등록 스킬의 격리된 복사본에서 우클릭 지점을 데이터 셀이 아닌 위치로 바꿨습니다. ‘같은 결과 표 안의 데이터 셀’로 보정할 수 있는 정책도 지정했습니다. 이 시험용 변경은 원본 녹화에 적용하지 않았습니다.

1. 실행기가 잘못된 지점을 감지해 3단계 우클릭 전에 멈췄습니다. 전체 호출은 6.853초였습니다.
2. 실제 입력 범위에 대한 승인 안에서 현재 표의 이미지를 가져왔습니다. 최종 구현에서 프레임 확인 호출은 3.528초였습니다.
3. 현재 이미지에서 데이터 셀을 확인해 3단계부터 이어갔습니다. 이미 처리한 필터 입력과 Enter는 반복하지 않았습니다. 재개 호출은 11.711초였고, 그 안의 엔진 실행은 8.160초였습니다.
4. 보정된 위치가 해당 복사본의 `workflow.json`에 저장됐습니다.
5. 새 Python 프로세스로 전체 업무를 다시 실행했습니다. 12.608초가 걸렸고 추가 보정 없이 같은 9단계를 마쳤습니다. 실행 전 읽기 검사는 이때도 한 번이었습니다.

시연, 첫 시험, 보정 후 재개, 새 프로세스 반복 실행의 네 XLSX 산출물을 별도로 읽었습니다. 모두 필터와 맞는 N 및 Hybrid의 3행이었고 Quantity는 11, 12, 13이었습니다.

실행기의 전체 결과는 `completed_unverified`와 종료 코드 3이었습니다. Enter와 Next, Proceed 호출은 전달까지 확인한 결과를 유지하기 때문입니다. 이번 시험에서 파일을 별도로 열어 확인한 사실과 각 호출의 검증 등급을 구분합니다. 종료 코드 3만 보고 같은 입력을 다시 보내면 안 됩니다.

## 범용 검증과 남은 한계

전체 자동 테스트 955개가 통과했습니다. 별도의 Windows 시험 창에서도 첫 메뉴 실행, 잘못된 지점의 보정, 중단 단계부터 재개, 새 프로세스 반복 실행과 원본 보존을 확인했습니다. 앱별 이름을 실행기에 하드코딩해 DBeaver에만 적용한 수정은 아닙니다.

이번 실제 실행의 호스트는 Codex였습니다. 호스트 모델이 자연어 설명을 읽고 제공된 명령으로 실행안을 준비하거나 화면을 확인하는 구조이며, Python 엔진 자체에 임의의 문장을 이해하는 모델이 내장된 것은 아닙니다. AX Workspace와 Claude Code용 사용 절차는 제공하지만, 이번 시험에서 실제 Claude Code CLI나 사내 모델까지 연결해 검증하지는 않았습니다.

회사 FX 환경은 이 PC에 없어 실제 FX 재검증은 하지 않았습니다. UIA에 전혀 드러나지 않는 화면이나 현재 이미지에서도 구분되지 않는 대상은 추가 관찰 또는 사용자 확인이 필요할 수 있습니다. 실제 마우스와 Enter를 쓰는 단계에서는 입력 충돌을 피해야 합니다.

첫 대상 포착에 걸린 9.225초는 남은 개선 과제입니다. 저장 후 등록과 재생, 위치 보정의 연결은 이번 시험에서 확인했지만, 녹화 시작의 지연까지 모두 해소됐다고 판단하지 않습니다.
